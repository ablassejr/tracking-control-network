\section{Code Migration: MATLAB to C++}
\label{sec:migration}

\subsection{Motivation}
\label{subsec:migration-motivation}

The original tracking control simulation was implemented as a collection of
MATLAB scripts (\texttt{cstr\_state\_tracking.m}--\texttt{cstr\_tracking\_error.m}),
following the reference implementation in \textsubscript{\cite{tymoshchuk2024tracking}}.
While MATLAB provides rapid prototyping through built-in matrix operations and
plotting, several factors motivated a migration to C++:

\begin{enumerate}
	\item \textbf{Execution speed.} The simulation loop iterates 45{,}000 time
	      steps with per-step nonlinear dynamics evaluation. C++ compiled code
	      with direct memory access eliminates the interpreter overhead inherent
	      to MATLAB's execution model.
	\item \textbf{Memory control.} C++ provides explicit control over stack
	      versus heap allocation, cache-aligned data layouts, and
	      zero-copy data access through pointers---critical when storing
	      $2 \times 45{,}000$ state matrices.
\end{enumerate}

\subsection{Architecture Decisions}
\label{subsec:migration-architecture}

The MATLAB implementation uses a procedural style: separate 1-D arrays for
each state variable (\texttt{x}, \texttt{y}, \texttt{r1}, \texttt{r2},
\texttt{e1}, \texttt{e2}, \texttt{u}) with a single \texttt{for} loop
driving the simulation. The C++ port uses 2d arrays for the state variables
with a single for loop as well. It adopts a struct-based architecture that
groups related data and separates concerns across compilation units.

\subsubsection{Data Layout}
\begin{table}[htbp]
	\centering
	\caption{Data structure mapping between MATLAB and C++ implementations.}
	\label{tab:data-layout}
	\begin{tabular}{lll}
		\toprule
		MATLAB Variable                        & C++ Equivalent                                 & Type                                \\
		\midrule
		\texttt{x(1:n)}, \texttt{y(1:n)}       & \texttt{stateMatrix}                           & \texttt{Matrix<double, 2, Dynamic>} \\
		\texttt{r1(1:n)}, \texttt{r2(1:n)}     & \texttt{referenceMatrix}                       & \texttt{Matrix<double, 2, Dynamic>} \\
		\texttt{e1(1:n)}, \texttt{e2(1:n)}     & \texttt{x1ErrorMatrix}, \texttt{x2ErrorMatrix} & \texttt{Matrix<double, 2, Dynamic>} \\
		\texttt{r2(i+1)-r2(i)}                 & \texttt{deltaReference}                        & \texttt{Matrix<double, 2, Dynamic>} \\
		\texttt{alpha}, \texttt{beta}, \ldots  & \texttt{InternalConditions}                    & \texttt{struct}                     \\
		\texttt{n}, \texttt{tmax}, \texttt{dt} & \texttt{SimSettings}                           & \texttt{struct}                     \\
		\bottomrule
	\end{tabular}
\end{table}

The key design choice is consolidating per-variable 1-D arrays into
$2 \times N$ Eigen matrices. Row~0 stores the conversion state
$x_1$, and row~1 stores the temperature state $x_2$. This layout
preserves temporal locality: accessing both states at time step $k$ requires
reading two adjacent memory locations in the same column.

\subsubsection{System Dynamics}
\label{subsubsec:dynamics}

The CSTR system has two states: conversion $x_1$ and temperature $x_2$.
Since the control gain $g_1 = 0$, the conversion state evolves under
open-loop natural dynamics. The temperature state uses feedback-linearizing
sliding-mode control.

\paragraph{Conversion state $x_1$ --- open loop.}
The natural dynamics follow the discretized CSTR model:
\begin{equation}
	x_1(k{+}1) = x_1(k) + \tau\!\left[
		-\alpha\, x_1(k) + D_a\bigl(1 - x_1(k)\bigr)
		\exp\!\left(\frac{x_2(k)}{1 + x_2(k)/\gamma}\right)
		\right]
	\label{eq:x1-dynamics}
\end{equation}

\textbf{MATLAB} (\texttt{cstr\_state\_tracking.m}, line~34):
\lstinputlisting[style=matlab, firstline=34, lastline=34]{\srcmatlab/cstr/clean/cstr_state_tracking.m}

\noindent
\textbf{C++} (\texttt{cstr\_dynamics.cpp}, lines~24--29):
\lstinputlisting[style=cpp, firstline=24, lastline=29]{\srccpp/cstr/cstr_dynamics.cpp}

The C++ version accesses parameters through the \texttt{InternalConditions}
struct rather than workspace variables, and uses cached pointer variables
(\texttt{prevX1}, \texttt{prevX2}) to avoid repeated matrix
indexing within the inner loop.

\paragraph{Temperature state $x_2$ --- closed loop.}
The feedback-linearizing control law cancels the nonlinear dynamics $f_2(x)$,
yielding the simplified closed-loop update:
\begin{equation}
	x_2(k{+}1) = x_2(k) + \tau\!\left[
	-\beta\,\operatorname{sgn}(e_2(k)) + \Delta r_2(k)
	\right]
	\label{eq:x2-closedloop}
\end{equation}
where $e_2(k) = x_2(k) - r_2(k)$ is the tracking error and
$\Delta r_2(k) = r_2(k{+}1) - r_2(k)$ is the reference change.

\noindent
\textbf{MATLAB} (\texttt{cstr\_state\_tracking.m}, line~68):
\lstinputlisting[style=matlab, firstline=68, lastline=68]{\srcmatlab/cstr/clean/cstr_state_tracking.m}

\noindent
\textbf{C++} (\texttt{cstr\_dynamics.cpp}, lines~32--35):
\lstinputlisting[style=cpp, firstline=32, lastline=35]{\srccpp/cstr/cstr_dynamics.cpp}

A notable difference is that the C++ implementation pre-computes the
$\Delta r_2$ matrix in a single Eigen operation before entering the simulation
loop, whereas MATLAB computes \texttt{r2(i+1)-r2(i)} inline at each step.

\subsection{Implementation --- Attacked CSTR System}
\label{subsec:migration-attacked}

The adversarial attack simulation extends the normal CSTR dynamics by
injecting additive Gaussian noise into the temperature state update at each
time step. The attack is implemented in both MATLAB
(\texttt{cstr\_state\_tracking\_attacked.m}) and C++ (\texttt{cstr\_state\_tracking\_attacked.cpp}), with the
core attacked dynamics defined in the shared
\texttt{attackedSystemFunction()} in \texttt{cstr\_dynamics.cpp}.

\subsubsection{Noise Injection}
\label{subsubsec:noise-injection}

The key difference from the normal system is the addition of a stochastic
perturbation $\epsilon(k) \sim \mathcal{N}(0, \sigma^2 \Delta t)$ to the
temperature state.

\noindent
\textbf{MATLAB} (\texttt{cstr\_state\_tracking\_attacked.m}, lines~31--37):
\lstinputlisting[style=matlab, firstline=31, lastline=32]{\srcmatlab/cstr/attacked/cstr_state_tracking_attacked.m}
\lstinputlisting[style=matlab, firstline=37, lastline=37, firstnumber=37]{\srcmatlab/cstr/attacked/cstr_state_tracking_attacked.m}

\noindent
In MATLAB, the noise sample is drawn via \texttt{randn()} scaled by
$\sigma \Delta t$, and is added only to the attacked $x_2$ update.

\noindent
\textbf{C++} (\texttt{cstr\_dynamics.cpp}, lines~46--73):
\lstinputlisting[style=cpp, firstline=46, lastline=47]{\srccpp/cstr/cstr_dynamics.cpp}
\lstinputlisting[style=cpp, firstline=70, lastline=73, firstnumber=70]{\srccpp/cstr/cstr_dynamics.cpp}

\noindent
The C++ implementation uses the \texttt{<random>} standard library with a

\subsection{Output Validation}
\label{subsec:migration-validation}

Verifying numerical equivalence between two independent implementations
requires more than visual comparison of plots. The migration includes a
CSV-based validation pipeline that compares the C++ simulation output against
MATLAB reference data at every time step.

\subsubsection{Validation Pipeline}

Both implementations export identical 7-column CSV files containing
$\bigl(t,\; x_1,\; x_2,\; r_1,\; r_2,\; e_1,\; e_2\bigr)$
at each of the $n = 45{,}000$ time steps. The MATLAB script writes its
reference data via \texttt{writematrix} at the end of the simulation loop;
the C++ executable writes its output through \texttt{std::ofstream} with
15-digit precision.

A standalone validation executable (\texttt{validate\_matlab\_cpp}) loads both CSV
files, extracts corresponding columns into Eigen vectors, and computes the
element-wise maximum absolute error for each variable:
\begin{equation}
	\varepsilon_{\max}^{(v)} = \max_{k=0}^{n-1}
	\bigl| v_{\text{C++}}(k) - v_{\text{MATLAB}}(k) \bigr|,
	\quad v \in \{x_1, x_2, e_1, e_2\}
	\label{eq:max-abs-error}
\end{equation}

Each variable passes if $\varepsilon_{\max}^{(v)} < \epsilon$ for a
configurable tolerance $\epsilon$. The validator reports per-variable
pass/fail status and returns a nonzero exit code on any failure, enabling
integration into automated build pipelines.

\subsubsection{Validation Results}

After correcting an off-by-one initialization error in the reference
trajectory (see \autoref{subsubsec:reference}), the validation confirms
machine-precision agreement between the two implementations:

\begin{table}[htbp]
	\centering
	\caption{Maximum absolute error between C++ and MATLAB outputs
		for the CSTR tracking control simulation
		($n = 45{,}000$, $\tau = 0.001$\,s).}
	\label{tab:validation-results}
	\begin{tabular}{lcl}
		\toprule
		Variable               & $\varepsilon_{\max}$ & Status \\
		\midrule
		$x_1$ (conversion)     & $\sim 10^{-15}$      & PASS   \\
		$x_2$ (temperature)    & $\sim 10^{-15}$      & PASS   \\
		$e_1$ (tracking error) & $\sim 10^{-15}$      & PASS   \\
		$e_2$ (tracking error) & $\sim 10^{-15}$      & PASS   \\
		\bottomrule
	\end{tabular}
\end{table}

The errors at $\mathcal{O}(10^{-15})$ are consistent with IEEE~754
double-precision machine epsilon ($\approx 2.22 \times 10^{-16}$),
confirming that the two implementations compute identical floating-point
results up to rounding in the final digits. The default tolerance of
$\epsilon = 10^{-6}$ provides a margin of nine orders of magnitude above
the observed error floor.
